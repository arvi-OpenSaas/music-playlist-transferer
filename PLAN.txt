================================================================================
  HarmonySync - Implementation Plan
  Phase 1: Apple Music -> YouTube Music
================================================================================

This plan turns HarmonySync into a production-ready Universal Music
Interoperability Platform. It prioritizes Clean Architecture, SOLID principles,
and a modular provider system so that Spotify, Amazon Music, JioSaavn, Gaana,
Tidal, Deezer, Napster, Pandora, SoundCloud, and future providers can be added
without redesigning the core application.

--------------------------------------------------------------------------------
1. CLARIFYING QUESTIONS (answer before implementation)
--------------------------------------------------------------------------------

1. Provider authentication / extraction strategy
   A) Use official APIs where available and content-script adapters only for
      platforms without a public API (recommended).
   B) Rely entirely on DOM scraping / page-JS interception for all platforms.

2. YouTube Music provider implementation
   A) Use YouTube Data API v3 (official but less precise for music matching).
   B) Inject scripts to call YouTube Music's internal browse/search endpoints.
   C) Manual "search + add" content-script flow in the web UI.

3. Apple Music authentication
   A) Use an Apple Developer token / MusicKit private key for API access.
   B) Authenticate via the signed-in web session at music.apple.com.

4. Local processing scope
   A) Run the full matching/scoring algorithm inside the service worker.
   B) Offload heavy string similarity to an offscreen document or web worker.

5. Data persistence requirement
   A) Queue state must survive browser restarts and worker kills (recommended).
   B) Queue state can be lost if the browser closes.

6. Testing expectations
   A) Unit tests for every pure module plus E2E mock-provider tests.
   B) Only unit tests for the core engine and matcher.

Answer these and I will begin building one file at a time.

--------------------------------------------------------------------------------
2. TARGET OUTCOMES FOR PHASE 1
--------------------------------------------------------------------------------

A Chrome Extension (Manifest V3) that can:

- Connect to Apple Music and YouTube Music.
- Read playlists and songs from Apple Music.
- Match each Apple Music song to a YouTube Music counterpart with a confidence
  score.
- Create a destination playlist in YouTube Music and add matched songs.
- Provide Pause, Resume, Cancel, progress updates, structured logs, and a
  transfer summary.
- Export missing, failed, and duplicate songs as JSON and CSV.

The architecture must allow adding a future provider by only creating:

  src/providers/<New>Provider.ts
  src/content/<newPlatform>.ts

No changes to TransferEngine, Queue, RetryEngine, Matcher, or Storage should
be required.

3. ARCHITECTURE OVERVIEW
--------------------------------------------------------------------------------

  +----------------------------------------------------------+
  |                         Popup UI                         |
  |  Transfer | Pause | Resume | Cancel | Logs | Reports     |
  +------------^-------------------------^-------------------+
               |                         |
        typed runtime messages    read settings / progress
               |                         |
  +------------v-------------------------v-------------------+
  |              Background Service Worker                     |
  |  +------------+  +----------+  +----------------------+   |
  |  |   Logger   |  |   Queue  |  |    RetryEngine       |   |
  |  +------------+  +----------+  +----------------------+   |
  |  +------------+  +----------+  +----------------------+   |
  |  | TransferEngine | Matcher |  | DuplicateDetector   |   |
  |  +------------+  +----------+  +----------------------+   |
  |  +------------+  +-------------------------------------+  |
  |  | IStorage   |  | MusicProvider interfaces / factory   |  |
  |  +------------+  +-------------------------------------+  |
  +------^----------------------^----------------------------+
         |                      |
    runtime messages       runtime messages
         |                      |
  +------v----------+    +------v----------+
  | AppleMusic      |    | YouTubeMusic    |
  | Content Adapter |    | Content Adapter |
  +-----------------+    +-----------------+

Design patterns used:
- Dependency Injection: every class receives collaborators through constructors.
- Strategy Pattern: MusicProvider, ScoringStrategy, StorageAdapter, RetryPolicy.
- Factory Pattern: ProviderFactory creates provider instances from ProviderName.
- Repository Pattern: IStorage abstracts chrome.storage away from business logic.
- Composition over inheritance.
- No God Classes. Maximum class size: 300 lines. Maximum function size: 40 lines.

5. DATA MODEL (canonical shapes)
--------------------------------------------------------------------------------

Song:
  id                  string          provider-specific id
  title               string
  artists             string[]
  album?              string
  durationSeconds?    number
  isExplicit?         boolean
  isLive?             boolean
  isRemix?            boolean
  isAcoustic?         boolean
  language?           string
  popularity?         number
  provider            ProviderName
  externalUrl?        string

Playlist:
  id                  string
  name                string
  description?        string
  songCount?          number
  provider            ProviderName
  externalUrl?        string

MatchResult:
  sourceSong          Song
  candidates          ScoredCandidate[]
  selectedMatch?      Song
  confidence          number
  action              'auto' | 'ask' | 'manual-review'

TransferReport:
  jobId               string
  sourceProvider      ProviderName
  destinationProvider ProviderName
  createdAt           number
  completedAt?        number
  totalSongs          number
  matched             MatchedSong[]
  failed              FailedSong[]
  missing             MissingSong[]
  duplicates          DuplicateSong[]
  status              TransferStatus

ProviderName enum:
  APPLE_MUSIC
  YOUTUBE_MUSIC
  SPOTIFY
  AMAZON_MUSIC
  JIOSAAVN
  GAANA
  TIDAL
  DEEZER
  NAPSTER
  PANDORA
  SOUNDCLOUD

Confidence thresholds (configurable):
  95-100  -> automatic match
  80-95   -> ask user
  below 80 -> manual review

PHASE F - Matching & Deduplication
----------------------------------

21. src/matcher/MatcherOptions.ts
    Purpose: matching configuration.
    Responsibilities: define weights for title, artist, album, duration,
                      language, explicit, popularity, live, remix, acoustic.
    Dependencies: types.ts.
    Communication: passed into Matcher/ConfidenceEngine.

22. src/matcher/ConfidenceEngine.ts
    Purpose: compute confidence scores.
    Responsibilities: fuzzy string similarity, duration delta, keyword detection,
                      explicit/popularity bonuses, return 0-100 score. Algorithm
                      is replaceable via strategy injection.
    Dependencies: types.ts, Helpers.ts, fuzzy string library, MatcherOptions.ts.
    Communication: Matcher calls this for each candidate.

23. src/matcher/Matcher.ts
    Purpose: smart song matching orchestrator.
    Responsibilities: take a source Song, ask destination provider to search,
                      score candidates using ConfidenceEngine, apply thresholds,
                      return MatchResult.
    Dependencies: MusicProvider.ts, ConfidenceEngine.ts, types.ts, errors.ts,
                  Logger.ts, MatcherOptions.ts.
    Communication: used by TransferEngine for each song.

24. src/matcher/DuplicateDetector.ts
    Purpose: detect duplicates.
    Responsibilities: hash/key comparison plus fuzzy fallback; report duplicate
                      songs in source/destination playlists.
    Dependencies: types.ts, Helpers.ts.
    Communication: called by TransferEngine before/after transfer.

PHASE G - Transfer Orchestration
--------------------------------

25. src/core/Queue.ts
    Purpose: persistent job queue.
    Responsibilities: enqueue transfer items, persist state in storage,
                      dequeue next item, mark success/failure, support
                      pause/resume/cancel, expose progress statistics.
    Dependencies: IStorage.ts, types.ts, Logger.ts.
    Communication: TransferEngine drives the queue; IStorage persists it.

26. src/core/RetryEngine.ts
    Purpose: retry policy executor.
    Responsibilities: exponential backoff, max attempts, classify errors as
                      retryable or fatal, integrate with HarmonySyncError.
    Dependencies: errors.ts, Logger.ts, constants.ts.
    Communication: TransferEngine calls before marking an item failed.

27. src/core/TransferEngine.ts
    Purpose: provider-agnostic transfer orchestrator.
    Responsibilities:
      - transfer(sourceProvider, destinationProvider, options)
      - fetch source playlists and songs
      - match each song (via Matcher)
      - enqueue and process queue
      - retry failures via RetryEngine
      - emit progress events
      - support pause/resume/cancel
      - generate report via TransferReportBuilder
      - never know concrete providers
    Dependencies: MusicProvider.ts, Queue.ts, RetryEngine.ts, Matcher.ts,
                  DuplicateDetector.ts, IStorage.ts, Logger.ts, errors.ts,
                  types.ts.
    Communication: instantiated by background; controlled by popup via messages.

28. src/core/TransferReportBuilder.ts
    Purpose: generate transfer summaries.
    Responsibilities: build TransferReport with counts; export JSON/CSV.
    Dependencies: types.ts, Helpers.ts.
    Communication: TransferEngine calls it at end; popup uses it for exports.

9. RISKS & MITIGATIONS
--------------------------------------------------------------------------------

Risk: YouTube Music has no fully public API.
Mitigation: build provider as content-script adapter; keep abstraction so it can
            be swapped later.

Risk: Apple Music DOM extraction is fragile.
Mitigation: use DOM observers and retries; prefer official API if a token is
            available.

Risk: Long transfers may be killed by service worker lifetime limits.
Mitigation: persist Queue in chrome.storage.local and resume on
            chrome.runtime.onStartup.

Risk: Song matching accuracy.
Mitigation: modular scoring strategy, configurable thresholds, and ask-user
            fallback.

Risk: Large playlists cause rate limits or UI freezing.
Mitigation: batched processing, throttled provider calls, async queue with
            pause/resume.
